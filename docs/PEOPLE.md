# 人を見つける（設計）

2026-10-24 時点の設計。恋愛マッチングは作らない（インターネット異性紹介事業の届出と年齢確認の義務、
双方向のコールドスタート、Fediverse の匿名文化との不一致）。代わりに、missmatch の
「言葉で探す → Clef で噛み合いを読む → スワイプで並べ替える」をそのまま使い、
**サーバーではなく「話が合いそうな人」をフォロー候補として並べる**。

## 1. 位置づけ

- Misskey は「ユーザーを探す」が人気順かローカルだけで、サーバーをまたいで「自分と話が合う人」を探す手段が無い。そこを埋める
- 片方向。相手の参加表明は要らない。公開ノートを書いていて、Misskey の設定で「アカウントを見つけやすくする」を有効にしている人だけを候補にする（§5）
- 「すき」「マッチ」の言葉は使わない。ボタンは **フォロー候補に入れる / スキップ**、一覧は **フォロー候補**
- ログイン不要で成立させる。MiAuth（read:account）は「自分のサーバーで開く」の補助に使い、フォロー済みの除外やワンタップフォローは権限を足す段階（§8 P3）まで持ち込まない

## 2. モード切替（UI）

ChatGPT / Claude の「チャット / Cowork」と同じく、**入力欄の直上にモードのセグメント**を置く。

```
┌──────────────────────────────────────────┐
│  ( サーバー ) ( 人 )          ← Segmented │
│  ┌────────────────────────────────────┐  │
│  │ ジャズと料理の話ができる人          │  │
│  └────────────────────────────────────┘  │
│  例文チップ（モードごとに差し替え）       │
└──────────────────────────────────────────┘
```

- モードは **検索（Search）の属性** `kind: 'server' | 'people'`。ランディングで選び、言葉を送った時点で固定される。既存の検索は `kind` 無し = `'server'`
- 言葉がある検索では、SearchBar の先頭に小さなチップ（🖥 サーバー / 👤 人）でモードを示す。途中でモードは変えない（変えたいときは「新しくさがす」）
- サイドバーの「さがした言葉」は両モードを同じ一覧に出し、行頭のアイコンで区別する
- ナビの 4 項目は共通。`people` の検索を開いているときは「いいね」を **フォロー候補**、「よくないね」を **スキップ** と表示する（バッジの数はその検索のもの）
- 例文（人モード）: 「ジャズと料理の話ができる人」「深夜に小説の話をしたい」「自作キーボード仲間」「病み期を否定しない人」など。サーバー例文と同じく cron で温める（§7）
- モバイルは同じセグメントを入力欄の上に置く。下タブバーは変えない

## 3. 画面

### カード（さがす）

左のカードはサーバーのカードと同じ大きさ・同じ操作（戻す / スキップ / フォロー候補）。

- 上段: アバター（64px）、表示名、`@user@host`、サーバー名のチップ（押すとサーバーの詳細シート = 既存の ServerDetails）
- 中段: 自己紹介 2 行（MFM は剥がす。カスタム絵文字は `:name:` のまま）
- 下段: 公開ノートの抜粋 2〜3 件（各 100 文字まで、URL・メンション除去）。これが「一致理由」の実体なので、噛み合い判定で効いた抜粋を優先して出す
- 右上: 相性ピル（サーバーと同じ #9ad11b）。チップ: 話題上位 2 つ、空気（ほのぼの / ドライ）、会話型 / 独り言型、投稿頻度（1 日 n 回）

### 右パネル（デスクトップ）

左と重複させない。Clef の判定を出す。

- 言葉との噛み合い（確率）
- 話題: 塗りのバー上位 3 つ
- 空気感・成人向け・身内ノリ: サーバーと同じ位置マーカー
- 事実: 投稿頻度、返信の割合、ノート数、アカウント作成からの月数、鍵アカかどうか（鍵アカは候補にしないので常に「公開」）
- 判定に使ったノート数と取得日時

### フォロー候補（一覧）

2 列のタイル（既存 LikesGrid の人版）。タイルからボトムシート / ダイアログで詳細。ボタンは 2 つ。

- **プロフィールを見る**: `https://{host}/@{username}`
- **自分のサーバーで開く**: `https://{myHost}/@{username}@{host}`。`myHost` はログイン中ならその host、未ログインなら「あなた」で入力した host（localStorage）。無ければボタンを出さず、ヒント「自分のサーバーを設定するとそこから開けます」

### あなた

既存の設定に 1 項目足す: **自分の Misskey サーバー**（ホスト入力。ログイン中は自動で埋まり編集不可）。人モードの絞り込み（§6 のハードフィルター）はサーバーの設定を流用し、人に効かない項目（登録のしかた・メアド等）は人モードでは畳む。

## 4. 候補の作り方（取り込みは全員、Clef は上位だけ）

サーバーで先に絞ると、小さな鯖にいる話の合う人をまるごと落とす。候補の絞り込みは Clef ではなく
**埋め込みベクトルの検索**で行い、Clef は **検索 1 回につき最大 40 人** にしか触れない。
これで Clef の本数が母集団の大きさに依存しなくなる。

```
取り込み（cron、Clef 不使用）
  LTL 100 件/サーバー/日（既存の投稿サンプリングと同じ呼び出し）
    ──→ 人ごとに公開ノートを蓄積（KV `notes:{host}:{userId}`、最大 20 件、14 日で消える）
    ──→ users/show を userIds 100 人ずつで叩き、isExplorable / isBot / isLocked を確認（サーバーごと 1 日 1 往復）
    ──→ 自己紹介 + 抜粋を 1 本の文章にして Workers AI（bge-m3）で埋め込み
    ──→ ベクトル表（KV の 1 ブロブ、int8 × 256 次元、§10）に追加。並びに host / cwRatio / notesPerDay / conversational を持つ
    ──→ 表示用の PersonCard（KV `person:v1:{host}:{userId}`、14 日）

検索（1 往復）
  言葉の並び ──→ 埋め込み 1 本 ──→ ベクトル表を Worker 内で総当たり → 上位 60 人（全サーバー横断。成人向け・除外 host・流速で絞る）
             ──→ KV から PersonCard を一括読み（100 鍵/操作）
             ──→ Clef 噛み合い: **上位 16 人だけ（1 バッチ）**。予算ガード（§10）に当たったら飛ばして類似度順のまま
             ──→ 雰囲気の軸（話題・空気・成人向け）は、出てきた人のうち未判定の分だけ Clef（応答後に waitUntil、14 日キャッシュ、1 日の上限あり）
             ──→ { people, affinity, answers } ──→ ブラウザで buildDeck ──→ 10 枚
```

- **1 人ずつ `users/notes` を取りに行かない**。misskey.io だけで数万往復になり、未認証のレート制限に当たる。LTL は公開ノートしか流れないので、可視性の判定も要らない
- 母集団は「直近 14 日に LTL に現れ、見つけやすくする設定が有効な人」。活発な人ほど早く入る
- 多様性（同じサーバーが 10 枚中 4 枚を超えない）はデッキを組む段で間引く。入口では削らない
- **スワイプ学習は埋め込みで行う**。いいね / スキップで検索ベクトルを寄せ（Rocchio: q' = q + 0.3·mean(liked) − 0.15·mean(passed)）、次の束はベクトル表に問い直す。Clef は追加で呼ばない。検索ごとに好みを分けるのは今と同じ

### PersonCard（KV `person:v1:{host}:{userId}`、14 日）

| フィールド | 内容 |
|---|---|
| host, userId, username, name, avatarUrl | 表示用。avatarUrl は各サーバーの URL をそのまま使う（`loading="lazy"`） |
| description | 自己紹介（200 文字まで、MFM を剥がす） |
| excerpts | 公開ノートの抜粋 8 件（各 120 文字、URL・メンション除去）。噛み合い判定とカード表示に使う |
| conversational | 返信（replyId あり）の割合。Clef を使わない |
| notesPerDay | 蓄積したノートの時間幅から算出。Clef を使わない |
| cwRatio | CW 付きの割合。成人向けの目安（ベクトル表の並びにも入れて検索時に絞る） |
| vibe | Clef の判定（genre / tone / nsfw / closedCommunity）。**出てきた人だけ**、1 日の上限内で読む。未判定なら null |
| seenAt, embeddedAt, version | 取り込みの時刻と埋め込みのバージョン |

ノート本文は excerpts 以外は `notes:` の蓄積にしか置かず、14 日で消える。

### 採点（ブラウザ内）

- 主: Clef の噛み合い（上位 16 人）。従: 埋め込みの類似度（60 人全員にある）。16 人の外側は類似度だけで並べ、束の後半に回す。予算ガードで Clef を飛ばしたときは類似度だけ
- vibe が無い人はハードフィルター（§6）を metadata の目安（cwRatio, notesPerDay, conversational）で代用する
- 多様性の間引きはここで行う

## 5. 候補にする条件と、しないこと

候補にするのは、次を**すべて**満たす人だけ。

1. Misskey の設定「アカウントを見つけやすくする」（`isExplorable`）が **true**。これは本家の「ユーザーを探す」に載せてよいという本人の意思表示で、missmatch も同じ基準に従う
2. `isBot` でない、鍵アカ（`isLocked`）でない、凍結・サイレンスでない
3. 直近 14 日の LTL で見かけ、蓄積した公開ノートが 5 件以上
4. サーバーが日本語で、LTL が公開されている（サーバーの対象と同じ）
5. 「あなた」の年齢が 18 歳未満のときは `nsfw` の高い人を出さない（サーバーと同じ）

しないこと。

- **非公開・ホーム限定・フォロワー限定のノートは読まない**（`visibility: 'public'` のみ）
- **誰が誰を見たか・候補に入れたか・スキップしたかをサーバーに残さない**。すべて localStorage
- **候補者の属性（性別・年齢・恋愛）を推定しない**。読むのは話題と空気だけ
- **ランキングを公開しない**。「このサーバーで一番〜な人」のような一覧は作らない
- **本人への通知をしない**。フォロー候補に入れても相手には何も届かない。実際のフォローは Misskey 側で行う

### 本人の意思の反映

- デッキに出す直前に `users/show` で `isExplorable` を **再確認**する（10 人分、1 往復）。設定を切った人は KV の期限を待たず消える
- 「この表示について」のリンクを人モードのカードの下に置き、候補になる条件と、外れる方法（Misskey の設定で「アカウントを見つけやすくする」を切る）を 1 画面で説明する
- サーバー運営者からの除外依頼は、サーバーの異議申立て（未決事項）と同じ導線に載せる。除外ホストは KV の `people:exclude` に置き、cron の温めと `/api/people` の両方で見る

## 6. 絞り込み（ハードフィルター）

人モードで効かせるのは次だけ。

| 設定 | 人モードでの意味 |
|---|---|
| 年齢 / R-18 | nsfw 軸の上限（サーバーと同じ） |
| 話したいこと | genre の加点（サーバーと同じ） |
| 空気 | tone の加点 |
| 流速 | notesPerDay の区分（静か / ふつう / にぎやか） |
| 会話の型（新設） | 会話型 / 独り言型 / こだわらない。`conversational` で絞る |

登録のしかた・メアド・広告・GTL・機能・運営の項目は人には効かないので、人モードの「あなた」では畳む。

読み取れない軸の聞き返し（AskChips）は、人モードでは **話題・空気・会話の型** の 3 軸だけ。

## 7. API と事前計算

- `POST /api/people` 入力 `{ turns, scope, vector?: number[] }`。`vector` はスワイプ学習で寄せた検索ベクトル（省略時は言葉から埋め込む）。出力 `{ people: PersonCard[], affinity: Record<id, number>, similarity: Record<id, number>, vector, answers, degraded: boolean }`。`vector` はブラウザに返し、次の束の問い直しに使う。`degraded` は予算ガードで Clef を飛ばしたしるし（UI は「簡易判定」と出す）
- `GET /api/people?ids=a,b` は PersonCard だけ返す（フォロー候補一覧の再描画用）
- 噛み合い判定は **7 日キャッシュ**（言葉の並び + 上位 16 人の id のハッシュが鍵）。雰囲気は 7 日おきにしか変わらないので 1 時間で捨てる理由が無い
- cron（1 日 1 回、既存の `scheduled` に足す）: 対象サーバーの LTL を読み、人を蓄積し、`users/show` で確認し、新規・更新のあった人を埋め込んでベクトル表を置き直す。1 回の上限は 1,000 人
- 人モードの例文 8 個は、サーバーの例文と同じく cron で噛み合い判定まで温める（8 × 1 バッチ、7 日おき）
- `PERSON_VERSION` を上げたら、埋め込みは次の cron から 1 日 1,000 人ずつ置き直す。版の違うベクトルは検索で除外する

### 新しく要るもの

- **Workers AI の埋め込みモデル**。候補は `@cf/google/embeddinggemma-300m`（768 次元、Matryoshka 学習済みで 256 次元に切り詰められる）、`@cf/pfnet/plamo-embedding-1b`（日本語特化）、`@cf/baai/bge-m3`（1,024 次元、100 万トークン 1,075 Neurons）。日本語の短い投稿での噛み方を eval で比べて 1 つに決める
- **Vectorize は使わない**（§10）。ベクトル表は KV の 1 ブロブ
- D1 は要らない

## 8. 段階

**P1（ログイン不要で成立）**

- `Search.kind`、ランディングのセグメント、人モードの例文
- cron の取り込み（LTL の蓄積、`users/show` の確認、埋め込み、ベクトル表の置き直し）
- `/api/people`、PersonCard、`person:` の KV、`users/show` での再確認
- 人のカード、右パネル、フォロー候補のタイル、「プロフィールを見る」「自分のサーバーで開く」
- 「この表示について」の説明ページ
- eval: 人モードの言葉 16 個と「上位に来てほしい人の条件」（話題タグ・サーバー）で recall@10

**P2（質）**

- 多様性の間引き、会話の型の聞き返し
- 例文の温め、cron を 1 日複数回に分ける
- 除外ホストと異議申立ての導線

**P3（ログインを活かす。権限を足すので別途判断）**

- `read:following` でフォロー済みを候補から外す
- `write:following` で「フォロー候補」からワンタップでフォロー。確認ダイアログ付き、権限は「あなた」で明示して任意にする

## 9. 未決

- **埋め込みの単位**: 自己紹介 + 抜粋を 1 本にまとめる案（ベクトル数 = 人数）と、ノートごとに埋め込んで人単位に集約する案（精度は上がるがベクトル数が 20 倍）を eval で比べる。「ジャズと料理の話ができる人」のような言葉と短い投稿の噛み方は実測しないと分からない
- **LTL の偏り**: 1 日 1 回の 100 件は瞬間的なので、連投する人に偏る。cron を 1 日 2〜3 回に分けるか、`sinceId` で前回の続きから読む
- **抜粋の選び方**: 噛み合い判定で効いた抜粋をカードに出したい。Clef の判定は確率だけで根拠の位置を返さないので、抜粋ごとに判定する（コスト 8 倍）か、言葉との単純一致で選ぶかを eval で決める
- **アバターの取得**: 各サーバーの URL を直接使うと、カード 10 枚で 10 サーバーに画像を取りに行く。重ければ Cloudflare Images の変換を挟む
- **CherryPick / Sharkey**: `isExplorable` の意味は同じだが、`users/notes` の形が違う場合がある。対象サーバーの本体種別で切り分ける

## 10. コストパフォーマンス設計（Workers AI の無料枠に収める）

### 前提の数字（2026-10、Cloudflare の料金表）

| 項目 | 値 |
|---|---|
| Workers AI 無料枠 | **1 日 10,000 Neurons**（全モデル合算、日本時間 9:00 にリセット） |
| 超過 | 1,000 Neurons あたり $0.011 |
| Clef | 入力 100 万トークンあたり 21,818 Neurons（$0.24）。**出力は無料** |
| bge-m3 | 100 万トークンあたり 1,075 Neurons |
| Vectorize 無料枠 | 保存 500 万次元（1,024 次元なら約 4,800 本、256 次元でも約 19,000 本）、検索 月 3,000 万次元 |

つまり **1 日に Clef へ入れられるのは約 46 万トークン**。埋め込みは Clef の 1/20 なので、設計はほぼ「Clef の入力トークンをどこに使うか」で決まる。

### 今の消費（人探しを足す前）

例文の温め: 16 言葉 × 13 バッチ × 約 4,000 トークン ≈ **83 万トークン / 日 ≈ 18,000 Neurons**。
これだけで無料枠の 1.8 倍。利用者の新しい言葉 1 つにつき 13 バッチ ≈ 52,000 トークン ≈ 1,135 Neurons。

### 設計の 4 本柱

**(1) 候補の絞り込みは埋め込み、Clef は 1 バッチ（16 件）だけ** — 人探しで使う形。ただし **サーバーには効かなかった**。

- 2026-10-24 の A/B（32 言葉、182 サーバー）: 全サーバー 13 バッチの recall@5 74% / @10 87% に対し、bge-m3 上位 16 件で 60% / 64%、48 件でも 66% / 72%。plamo-embedding-1b が最良で 69% / 77% だが応答 4.7 秒。「英語で話せる」「静かな場所」のように意味で決まる言葉を埋め込みが拾えない。字面の一致を足しても戻らなかった（REQUIREMENTS.md 未決事項）
- サーバーの噛み合いは **1,135 Neurons / 言葉のまま**。下げるなら対象を減らすのではなく、1 サーバーあたりの state（説明 300 字 + ルール 200 字 ≈ 250 トークン）を削る方向で、eval で精度を見ながら決める
- 人探しでは候補が数千〜数万人なので、Clef を全員にかける選択肢が無く、埋め込みで絞るしかない。サーバーで落ちた「意味で決まる言葉」は人でも落ちる前提で、K を 16 ではなく 32〜48（2〜3 バッチ、175〜260 Neurons）にし、自己紹介の抜粋を多めに埋め込む。精度は人探しの eval で別に測る

**(2) キャッシュは 7 日** — 雰囲気は 7 日おきにしか変わらない。噛み合い判定（`intent:` と人の分）を 25 時間から 7 日に延ばし、cron の温めは「期限切れの分だけ」にする。例文 16 + 8 の温めは **1 日あたり 1/7 ずつ ≈ 300 Neurons**

**(3) 人の雰囲気は「出てきた人だけ、1 日の上限内で」** — 1 人の判定は状態 300 トークン + 設問 15 本 ≈ 400 トークン ≈ 9 Neurons。上限 300 人 / 日 ≈ 2,700 Neurons。超えた分は翌日に回し、それまでは埋め込みの類似度と cwRatio などの目安で代用する

**(4) 予算ガード** — Clef の応答にある `usage.input_tokens` を KV の `ai:neurons:{日付}` に加算し（21,818 / 100 万で換算）、1 日 9,000 を超えたら:

- 噛み合い判定を飛ばし、類似度順で返す（`degraded: true`、UI は「簡易判定」）
- 人の雰囲気の追加判定と cron の温めを止める
- 既にキャッシュにある判定はそのまま使う

これで「品質が下がる日はあっても、請求が発生する日は無い」を仕組みで保証する。埋め込みは安いのでガードの対象外（1 日 1,000 人 × 300 トークン ≈ 320 Neurons）。

### 1 日の予算配分（10,000 Neurons）

| 用途 | 単価 | 1 日の目安 | Neurons |
|---|---|---|---|
| サーバー例文の温め（16 個、7 日おき） | 1,135 | 約 2.3 本 | 2,600 |
| サーバーの新しい言葉（絞らない） | 1,135 | 4 言葉 | 4,500 |
| 人の例文の温め（8 個、7 日おき） | 260 | 約 1.1 本 | 300 |
| 人の新しい言葉（K=48、3 バッチ） | 260 | 5 言葉 | 1,300 |
| 人の雰囲気（初出の人） | 9 | 100 人 | 900 |
| 埋め込み（人 1,000 + サーバー 80） | 0.3 | — | 350 |
| 予備 | | | 50 |

サーバーの言葉が 1 日 4 個を超える日は超過分が課金になる（1 言葉 ≈ $0.012）。実際の使用量は `ai:neurons:<UTC 日付>` に残るので、1〜2 週間見てから人探しの配分を決める。超えた日も結果は劣化させない（§10 の予算ガードは温め・欠け埋め・先読みだけを止める）。

### ベクトル表は Vectorize ではなく KV の 1 ブロブ

- 256 次元 × int8 なら 1 人 256 バイト。2 万人で 5 MB、KV の上限（25 MB）に収まる
- Worker 内で総当たり（2 万人 × 256 次元 ≈ 500 万回の積和）は数ミリ秒。isolate のメモリに 1 時間置いて使い回す
- 埋め込みの切り詰め（768 → 256）は Matryoshka 学習済みのモデル（EmbeddingGemma）なら品質の損失が小さい。bge-m3 を選ぶなら切り詰めず 1,024 次元 × int8 = 1 KB / 人（2 万人で 20 MB）
- Vectorize を使わない理由: 無料枠の保存上限が 1,024 次元で約 4,800 本と小さく、バインディングと別料金体系が増えるわりに、この規模では総当たりで足りる。5 万人を超えたら Vectorize に移す
- Workers Free プラン（CPU 10 ms / リクエスト）なら総当たりは 5,000 人程度が上限。Workers Paid（CPU 30 秒）なら問題ない
